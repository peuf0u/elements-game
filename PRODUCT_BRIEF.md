# Elements — Product Brief

What we're building and the product decisions made so far. Game rules live in [GAME_SPEC.md](GAME_SPEC.md); this file covers everything around them.

## Goal

Turn the Elements board game into a digital game that friends can play together, starting on iPhone and iPad.

## Decisions

| # | Decision | Date |
|---|---|---|
| D1 | **First version is same-device play**: two players on one iPad/iPhone, taking turns. No server, no accounts. | 2026-10-27 |
| D2 | **Online play between friends comes later**, as a second iteration. | 2026-10-27 |
| D3 | **iPad is a first-class target**: the game must play *well* on iPad, not just scale up from the phone. | 2026-10-27 |
| D4 | **Cross-platform is wanted**: iOS and iPadOS first, with web and Android (and whatever comes next) without a rewrite. | 2026-10-27 |
| D5 | **The rules engine is pure and platform-independent**: game state and moves are plain, serializable data, and the engine just turns (state, move) into a new state. This keeps D2 cheap, because the same engine can run on a server or a second device later. | 2026-10-27 |
| D6 | **v1 = core rules only**; proposed mechanics and rule experiments come in as variant toggles (see GAME_SPEC.md "v1 scope"). | 2026-10-18 |
| D7 | **TypeScript end to end.** The rules engine is a standalone pure TypeScript package (`packages/engine`) that the app, the AI bot worker and a future server import unchanged. Both short-listed app stacks use it. See [tech-stack research](docs/research/tech-stack.md). | 2026-10-27 |
| D8 | **Engine architecture** follows [architecture research](docs/research/architecture.md): immutable public API, the game stored as its action log pinned to a rules version, moves as `(from, to)`, pseudo-legal generation plus a Wizard-safety filter, variants as a config object, and one player interface for local, bot and remote players. | 2026-10-27 |
| D9 | **Presentation (final): PixiJS 8 + GSAP for the board, inside a React + Vite app shell, wrapped with Capacitor** for the App Store and Play Store; the same build is the website. Chosen for its higher ceiling for a rich, game-like interface (effects, a later 3D mode), built-in accessibility and team maintenance. The first board build is checked on a real iPad for sharpness, Stage Manager/Split View resizing, smooth dragging (including Low Power Mode) and no stutter while the bot thinks. **Alternative candidates**, if Pixi falls short on a check it can't fix: Konva (simplest interaction model) and Phaser (full game framework, project-health concerns). See [2D game framework research](docs/research/2d-game-frameworks.md). | 2026-10-27 |
| D10 | **The game is a self-contained module** (`mountGame(element, hostPort)`: board, session and bot) that talks to its host only through a small, versioned JSON message protocol. Haptics and storage are requests to the host. The React shell uses it in the same process from day one, and a native SwiftUI or Compose shell can host it later in a WebView without rework. See [2D game framework research §6.8](docs/research/2d-game-frameworks.md). | 2026-10-27 |
| D11 | **Build approach: a throwaway spike first, then a proper incremental build.** The spike is a quick playable version to try the game on screen. Architecture doesn't matter there; it lives in its own `spike/` folder and is never promoted to production. If the game works on screen, it is rebuilt properly and incrementally (a walking skeleton: a thin slice through all layers first, then one rule at a time), step by step so the designer understands the structure. Lessons from the spike go back into GAME_SPEC.md and this brief. | 2026-10-27 |
| D12 | **Computer playtesting lives in its own `playtest/` folder**, separate from the spike and the real app. Computer players play thousands of games to check balance, game length, endings and dominant strategies. The players reach the rules only through one connector file (`playtest/engine.mjs`), which reads the spike's rules today and switches to `packages/engine` once that exists, so the same experiments then also check that the real app plays the same game. The players can later grow into the app's bot opponent; whether the app takes the code or rebuilds it step by step (D11) is decided when the bot is built, starting from what playtesting showed works (piece values, look-ahead depth, speed). | 2026-10-28 |
| D13 | **The real rules engine is started now, in `packages/engine`** (TypeScript, D7), because the playtest needed rules about 10× faster than the spike's. It follows D8: an immutable public API for the app and server, plus a fast mutable core (make and take back moves) that the bots search with. The rules exist once, and both ways in share one move generator. This is a change from the architecture research's suggestion A1, which would have put the fast board in a separate bot package and so given the rules a second copy. The engine covers the play phase first; the formation phase follows. It is checked against the spike: perft totals and random-game comparisons give identical legal moves, in the same order, under every variant, so all earlier playtest results stay valid. The playtest reaches it through `playtest/engine.mjs` only. Chess calibration for the playtest (comparing the method against known chess results) gets its own small chess move generator in `playtest/`, checked against published perft numbers. | 2026-10-28 |
| D14 | **The spike is public, with a computer opponent**, at https://elements-game-kappa.vercel.app (Vercel project `elements-game`), so other people can try the game before the real app exists. It is still the throwaway spike (D11). The opponent is the playtest's bots (D12) on the real engine (D13), run in a Web Worker: Easy is Careful, Medium is Deep with a 2,000-position budget and Hard is Deep with 20,000, both with the learned piece values (rated 1000, 1690 and 1942 in [playtest/FINDINGS.md](playtest/FINDINGS.md) §10). The board keeps the spike's own rules; the engine lists the same moves in the same order (`playtest/check.mjs`). To match the spec, the public spike uses the 75-move rule and the new default formation and presets, and drops the exact-range option. The computer places its pieces one at a time from the default formation. `spike/build.mjs` builds it; `vercel deploy --prod` from the repo root publishes it (no Git connection yet). | 2026-10-28 |

## Open

- **Spike scope and delivery**: what the spike includes, and how to open it on the iPad.
- **v2 backend**: Firebase vs Supabase, decided when online play starts.
- **Native shells** (SwiftUI and Compose): not for v1. Reconsider for v2 online play (friends, notifications, Game Center). D10 keeps that door open.
- **Accounts**: Apple Developer ($99/year) and Google Play ($25 once). New personal Play accounts must run a closed test with 12 testers for 14 days before release, so start that early.
- **Undo policy**: suggested free undo on a shared device, undo by request online, configurable against the bot (architecture research A7).
- Visual identity: names and look of the two sides, and the form of the element pieces (GAME_SPEC.md deferred Q5).
  - Spike, 2026-10-27: the designer is trying one shape per element, hinting at how it moves (Fire square, Wind diamond, Water drop, Earth octagon; the Wizard stays a star). A two-element stack is drawn as seen from above: the bigger piece's shape underneath, the other as a small shape on top (overlaid outlines were tried first, and the designer preferred the stacked look). With Earth, the attacker is always underneath, because the stack moves only as the attacker. A stack shows one set of dots, its range. Each side has its own shade of every element colour (lighter for White, deeper for Black) on top of the thin owner rim; a centre cap like the pyramid tip and a thick rim were tried and set aside. The board drops the chess-style checkers: each zone is a separate plate of sandstone tiles, warmer at home and paler in the middle (preferred over a plain paper grid, tinted zones, marble and basalt, slate, terracotta, pebbles and a carved block). Not decided yet.
- Same-device UX on iPad: rotate the board between turns, or keep one orientation that reads from both sides?
- How online play works (D2): turn-based over days with notifications, or live sessions, or both.
- **Setup safety** (computer playtesting, 2026-10-28, [playtest/FINDINGS.md](playtest/FINDINGS.md) §6): a careless formation can lose at once. In 3 of 300 games with random formations the game was over within 3 moves each, once by checkmate on White's first move. Should the formation phase warn about a Wizard that can be mated in one, or steer new players to presets? A formation search (§8) found several formations about as strong as the default (in `playtest/formations.mjs`), so a small set of presets is possible without favouring one. Avoid presets with Earth on both sides of the Wizard: that "Earth shield" scored only 29% against the default.
- **Bot opponent difficulty** (D12): on a Mac, Careful takes about 0.07 s per move and Thinker about 0.4 s. Each one beats the level below 92–99% of the time, so Greedy, Careful and Thinker are natural candidates for easy, medium and hard. To check: speed on an iPad, and whether Careful is beatable but not trivial for a new human player.
